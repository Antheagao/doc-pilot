### What the code says today (facts the plan depends on)

- Every model call goes through one constructor, `extraction._build_client(settings)` (`backend/app/extraction.py:215`): extraction (`messages.create`, forced `record_extraction` tool), transcription (`messages.create`, no tools, `transcribe_v1` system prompt), the agent loop (`beta.messages.create` with `TOOL_DEFINITIONS`), the eval and online judges (`beta.messages.create` with `output_config.format` JSON schema).
  The API caches one client in `routers/ask.get_anthropic_client`, which returns `None` (route answers 503) when there is no key.
- Cost is always computed by doc-pilot from token counts and `PRICING_PER_MTOK` (`_usage_cost_usd`, `_compute_cost_usd`, `loop.call_cost_usd`), never taken from the API.
- Existing fakes: the eval `build_mock_extract_fn` (replaces `extract_document`, so it skips the client, the repair path, and the worker), the `SimpleNamespace` scripted client plus `validate_request` in `tests/test_agent.py` (test-only), the demo seed's replay of committed Sonnet answers (`app/demo_seed._replayed_tool_input`, writes rows directly, no queue), and `HashingEmbedder` vs `FastEmbedEmbedder` (ONNX, threads unbounded by default; fastembed 0.9.0 accepts `threads=`).
- The base compose file passes `ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}` to `api` and `worker` from the root `.env`, which holds the real key; the demo overlay inherits it.
  Any new overlay must blank it explicitly, or it bills.
  The Anthropic SDK also reads `ANTHROPIC_API_KEY` from the process environment on its own if any code builds a client without one.
- **The worker is not safe to scale today.**
  `reclaim_orphaned_jobs` at startup with no lease resets every `processing` job (so a second container steals the first one's in-flight jobs), and `complete_job` / `fail_job` write unconditionally (no compare-and-set); `docker-compose.yml` says "never `--scale worker=2`".
  `WORKER_RECLAIM_AFTER_SECONDS` exists (a lease), but the completion side still needs compare-and-set before 2, 4 and 8 workers mean anything.
- The engine is `create_async_engine(settings.database_url)` with SQLAlchemy defaults: pool 5 plus overflow 10, 30 s pool timeout, one engine per process; Postgres `max_connections` is the image default 100; the API is one uvicorn process (`backend/Dockerfile` CMD, no `--workers`), and the rate limiters are in process memory, which assumes that.
- `POST /ask` takes its session from `get_session`; `enforce_daily_budget` begins a transaction on it, and the agent's tools run inside it, so a pooled connection stays checked out (idle in transaction) across every model call of the run.
  `POST /ask/stream` holds the request's session (budget check) for the whole stream and opens a second one for the run: two connections per stream.
- `enforce_daily_budget` on every upload and question calls `docpilot_spend_since`, which sums every organization's extraction, page, and answer rows since midnight UTC: its cost grows with the rows written today, which during a load run is all of them.
- Under row-level security the GIN index cannot serve `tsv @@ query`, so lexical search (and `_term_idf`'s chunk counts) reads the whole tenant's chunks through `ix_document_chunks_organization_id` (database overlay, measured plans).
- Machine: Apple M1 (4 performance plus 4 efficiency cores), 16 GB; Docker Desktop 29.4.0 with 8 CPUs and 7.75 GiB; `pgvector/pgvector:pg16-trixie` is PostgreSQL 16.15 and ships `pg_stat_statements` (checked in a throwaway container).
- Committed artifacts already carry per-document `latency_ms`, `input_tokens`, `output_tokens` (Sonnet v1: p50 5,165 ms, p95 10,995 ms over 25 docs; Haiku v1: p50 3,651 ms); there is no committed live agent or judge run, so their latencies have no artifact.
- Ports in use: dev 5434/8000/3000, demo 8100/3100, others 5432, 5433, 5435, 5436, 8080; 8200, 16786, 4418 are free.

### Key design decisions (planner defaults; Anthony can override)

- **The scripted model lives in `app/` (`backend/app/scripted_model.py`), behind `_build_client`, selected by `MODEL_PROVIDER=scripted`.**
  The load stack runs the production image, which holds only `backend/app` (not `tests/`), so a test-only fake could not run inside the real worker and API; `HashingEmbedder` and `demo_seed` are the precedent for an explicit, opt-in stand-in in `app/`.
- **It is a drop-in client, not a new interface at every call site.**
  `ScriptedModelClient` exposes `messages.create` and `beta.messages.create` and returns real SDK types (`anthropic.types.Message`, `anthropic.types.beta.BetaMessage`, `BetaTextBlock` with `BetaCitationSearchResultLocation`, `ToolUseBlock`, `Usage`), so `record_model_response`, `_echoable`, `_assemble_answer`, `_resolve_citation`, the repair path, and the pricing code run unchanged.
  It routes by request shape (forced `record_extraction` tool; the transcription system prompt; `TOOL_DEFINITIONS`; a JSON-schema `output_config.format`), and an unrecognized or malformed request raises `anthropic.BadRequestError` like the real API (Liskov: a stand-in fails the same ways).
- **It answers from committed data, so the real paths do real work.**
  Extraction replays what the committed Sonnet run returned for that document and schema (the demo seed's replay, moved to a shared `app/evals/replay.py`), else the label at confidence 0.9 with gold evidence, so reconciliation, review routing, and the review queue see real misreads and low-confidence fields.
  A document is recognized by the SHA-256 of its pixel content (PNG `IHDR`/`IDAT`/`IEND` chunks; ancillary text chunks ignored), so the load generator can make every upload byte-unique with a `tEXt` nonce and still be "read" as its corpus document; unknown bytes get a fixed generic answer at confidence 0.5 (routed to review).
  Transcription returns the document's gold page text plus one line `Ref <12 hex of the full-bytes digest>`, so chunk text and vectors are unique per upload (identical vectors would make HNSW and IDF numbers artificial).
  The agent follows a fixed policy: `query_extractions` for a question with an amount or "total/spent/how much", else `search_documents`; then `get_page` on the top hit; then an answer citing up to two returned `search_result` blocks by their real `source` and block indices, so citations resolve through the real code.
  The judge returns a schema-valid verdict built from the requested JSON schema.
- **Cost is $0 by the real pricing code, and rows say so.**
  `MODEL_PROVIDER=scripted` requires every model setting (`EXTRACTION_MODEL`, `TRANSCRIPTION_MODEL`, `AGENT_MODEL`, `JUDGE_MODEL`) to be `scripted`, priced `ModelPrice(0, 0, 0)` in `PRICING_PER_MTOK` with a comment; `MODEL_PROVIDER=anthropic` refuses the model name `scripted`.
  So every stored row and span names the scripted model, token counts are real numbers from a documented formula, and cost is computed, not hard-coded.
- **Latency and tokens are deterministic and configurable.**
  `SCRIPTED_MODEL_PROFILE=zero|replay` and `SCRIPTED_MODEL_LATENCY_SCALE` (float, default 1.0); `replay` takes extraction latency and tokens per document from the committed Sonnet v1 artifact and transcription from the Haiku v1 artifact (a proxy, labeled), and agent step and judge latency from two settings (`SCRIPTED_AGENT_STEP_MS` 3000, `SCRIPTED_JUDGE_MS` 4000, labeled assumptions because no live run is committed).
  Sleeps go through an injected `sleep` callable so tests assert exact delays; there is no randomness.
- **A load run can never bill, by four independent layers.**
  (1) The load overlay sets `MODEL_PROVIDER=scripted`, the four model names, and `ANTHROPIC_API_KEY: ""` on `api` and `worker`.
  (2) `Settings` refuses `scripted` together with a non-empty key unless `SCRIPTED_MODEL_ALLOW_API_KEY=true` (for a host-run process that reads `backend/.env`; the scripted path never builds an Anthropic client, but an empty key also disarms the SDK's own environment lookup), and refuses a non-`scripted` model name.
  (3) The harness preflight asks every `api` and `worker` container for `(model_provider, bool(key))` (a yes or no only, like `demo.py api_has_key`) and refuses to send traffic unless all are `("scripted", False)`.
  (4) The overlay keeps the daily budget on at `DAILY_BUDGET_USD=0.01`, so any recorded spend over a cent turns uploads and questions into 429s; the postflight asserts `docpilot_spend_since(today) = 0` and that no extraction, page, or answer row names a model other than `scripted`, and the artifact records `spend_usd: 0`.
- **Locust 2.47.0, not k6.**
  Locust's `HttpUser` timestamps each SSE frame of `/ask/stream` (time to first event and to the answer), proven above, while stock k6 buffers the stream; the scenarios, the SSE parser, percentile math, and the artifact builder are Python in this Python repository, unit-tested with pytest; `load.py` (stdlib, on the host) drives each phase, starting headless Locust in the `loadgen` container with the phase's parameters and reading back its per-sample file, while it runs the samplers and the worker scaling itself, so one program owns the timeline and writes the one artifact (every sample carries a UTC wall-clock stamp; Docker Desktop's VM clock is synced to the host).
  Locust's own percentiles are bucketed, so the harness records every sample itself and computes exact percentiles; the generator's CPU is sampled and recorded, and a phase whose generator exceeds 80% of a core is marked invalid.
  k6's strengths (lower generator overhead, built-in thresholds) matter less here: a single uvicorn process saturates long before one Locust process does, and CI needs only a pinned pip package.
- **The generator runs inside the load project's network** (a `loadgen` service, profile `loadgen`, `scripts/load/Dockerfile` on `python:3.12-slim` with `scripts/load/requirements.txt` pinning `locust==2.47.0`), hitting `http://api:8000`, so the numbers exclude Docker Desktop's host port forwarder; it competes for the same 8 vCPUs, which the artifact records.
- **A dedicated compose project `doc-pilot-load`** (`docker-compose.load.yml`, the demo overlay's pattern): its own images (`doc-pilot-load-backend`), database `docpilot_load` with no host port, volumes `doc-pilot-load_*`, API on `127.0.0.1:8200` for inspection, no frontend (moved to a profile), Jaeger under `tracing` on `127.0.0.1:16786` and `4418`, Postgres started with `shared_preload_libraries=pg_stat_statements`, and the runtime role `docpilot_runtime` provisioned by `migrate`, so Batch N's startup guard passes.
  The project-pinned compose helpers and the volume guard move out of `scripts/demos/demo.py` into a shared `scripts/compose_project.py` (`ComposeProject(name, files)`), which both CLIs use with their own constant project, so the guard is written once.
- **Tenants and sign-in through the real auth.**
  `load.py seed` creates three organizations through `scripts/accounts.py` (`load-large`, `load-medium`, `load-small`, so RLS, the per-tenant scans, and a small tenant among large ones are all exercised), one owner each with `--password-stdin`, and one API key each (captured from stdout into memory and the gitignored `scripts/load/out/`, never into an artifact).
  Most virtual users authenticate by API key (`Authorization: Bearer dpk_...`); one user class per tenant signs in once with `/auth/login` (argon2, real cookie, `Origin` on writes), staying under the sign-in limits.
  Load-only overrides, recorded in the artifact: `ASK_RATE_LIMIT_PER_MINUTE=0`, `UPLOAD_RATE_LIMIT_PER_MINUTE=0`, `ASK_JUDGE_SAMPLE_RATE=0.25` (judge jobs ride the queue), `WORKER_RECLAIM_AFTER_SECONDS=600`, Langfuse off, tracing off except in the diagnosis pass.
- **Measurement method.**
  Ingest: with workers scaled to 0, upload a fixed set through `POST /documents` at stepped concurrency (pure API ingest throughput and latency).
  Worker scaling: for N in 1, 2, 4, 8, reset the database and uploads volumes (models kept), upload a backlog of B documents with 0 workers, then `up -d --scale worker=N`; throughput is completed jobs between the 10% and 90% completion marks divided by that time (robust to staggered starts and the tail), and queue depth by state and kind is sampled every second by the owner inside the db container (the runtime role cannot see across tenants).
  Read ramp: a fixed mix per tenant (70% `/search` hybrid, 15% `/ask`, 10% `/ask/stream`, 5% `GET /documents`) at 2, 4, 8, 16, 32, 64 users, 60 s per step; "breaks" means error rate over 1% or `/search` p95 over a pre-registered 1 s SLO; the knee is the last step that meets both.
  Each measured configuration runs three times and the table shows the median with the min-max range; before and after use the same scenario digest.
- **Artifacts in `scripts/load/results/<run_id>_<label>.json` (`load_v1`)**, not `evals/results/`: the API mounts `evals/results` for `/monitoring/evals` and `/stats`, and a non-eval suite there would need a skip rule in `app/evals/history.py`.
  Each artifact records the git commit and dirty flag, `sys.argv`, the machine (`sysctl` CPU, core counts, memory, macOS version), Docker (`docker info` version, NCPU, memory), Postgres and pgvector versions, `max_connections`, the API and worker pool sizes, uvicorn worker count, embedder, every load-only override, the model profile and scale, tenant sizes (documents, chunks), per-phase per-endpoint counts, errors, rps and quantiles (p1 to p99 plus p99.9, not raw samples; raw samples go to gitignored `scripts/load/out/`), queue-depth series, per-container CPU and memory series from `docker stats`, the top `pg_stat_statements` rows by total time (statement text, calls, mean and total ms), pg_stat_activity counts by `application_name` and state, generator CPU, and `spend_usd`.
- **README generation like the eval tables.**
  `scripts/load/report.py` (stdlib only) renders the region between `<!-- PERF_TABLE:START -->` and `<!-- PERF_TABLE:END -->` and two SVGs, `screenshots/performance/load-light.svg` and `load-dark.svg`, shown with `<picture><source media="(prefers-color-scheme: dark)">`, which follows GitHub's theme; colors are the dashboard's CVD-checked series slots (`--series-1..4` from `frontend/src/app/globals.css`, light and dark values) for 1, 2, 4, 8 workers, with a legend and end labels so identity never rests on color, `<title>` and `<desc>` for screen readers, and text in the theme's foreground.
  Panel 1: jobs/s against workers with the ideal linear line; panel 2: pending jobs over time per N.
  The report refuses an artifact that is dirty, not scripted, or has nonzero spend, and refuses a before and after pair whose machine, Docker resources, profile, scale, scenario digest, or overrides differ.

## Batch M - MCP server over the agent tools (added 2026-10-25)

Planned by the planner against master `63981b7`, from item 3 of the portfolio queue (`project-dossier/PROJECT-QUEUE.md`); worked while Batch B's last two tasks wait (B11b needs approval, B12 needs the v3 routing fix first).
Goal: the three `/ask` tools (`query_extractions`, `search_documents`, `get_page`) served to any MCP client over stdio and streamable HTTP, with the same execution path, caps, and untrusted-data handling as `/ask`.
The MCP server never calls the model: the MCP client is the model, so doc-pilot spends nothing.

Key design decisions (planner defaults; Anthony can override):
- `mcp` 2.3.0, low-level `Server` (not `MCPServer`, which derives schemas from signatures and would fork `TOOL_DEFINITIONS`); the API was read from the installed package, not from memory: FastMCP is gone in 2.x, and a 2026-07-28 stateless protocol era sits beside the 2025-11-25 handshake era.
- One execution path: `loop._run_tool`'s body moves into `tools.execute_tool`, which `/ask` and MCP both call, so the two cannot drift.
- Arguments are validated against the advertised schema in code (the low-level server does not, and MCP clients give no `strict` guarantee); string arguments are capped at 500 characters.
- Results are one framed text block (a fixed untrusted-data notice, then document text between `BEGIN DOCUMENT DATA <nonce>` / `END DOCUMENT DATA <nonce>` with a fresh nonce per call) plus `structuredContent` under an `outputSchema` carrying the `doc-pilot://` source URIs; capped by `MCP_MAX_RESULT_CHARS` (24,000).
- Card numbers in page text are masked when the tools read it (`_line_blocks`), so `/ask` gains it too.
- HTTP is a plain `Route("/mcp")` on the API (a `mount` answers 307 to everything), stateless JSON mode, Host limited to loopback, any `Origin` refused, then the API's own rate limiter in an `mcp` bucket (`MCP_RATE_LIMIT_PER_MINUTE`, 120).
- Deferred to the auth item (portfolio queue item 4): API keys, per-key document scope and rate buckets, non-loopback access, browser origins, a tool-call audit log, MCP resources.

## Batch B - Extraction schema v2: richer fields plus evidence (promoted 2026-10-14, expanded 2026-10-15)

Expanded by the planner against master `3d25754`.
Goal: capture what real invoices carry, and make every leaf say where it came from.
Zero-spend work comes first; B10, B11, and B11b spend money and each needs Anthony's approval before it runs.

Key design decisions (planner defaults; Anthony can override):
- Storage: JSONB leaves, no new columns, no backfill. Every v2 leaf is `{value, confidence, evidence: {page, quote} | null}`, cells of `line_items` and `tax_lines` included; v1 extractions keep their 7 rows untouched.
- v1 and v2 coexist through a schema registry keyed by `prompt_version` (`app/extraction_fields.py`: `ExtractionSchema`, `SCHEMAS`, `schema_for`); the worker extracts with `Settings.extraction_prompt_version`, default `extract_v1` until the paid eval passes a pre-registered bar. v1 stays byte-identical.
- API and UI: no new endpoint; evidence rides inside the leaves. Tax-line `rate` is the printed percent as a plain decimal string; code divides by 100.
- `rules_v2` on a v1 record gives exactly the `rules_v1` verdicts (a v2-only check is emitted only when one of its v2 operands is present), pinned by a golden fixture, so the published numbers do not move.
- A quote mismatch gets its own review reason, `quote:<path>`, as a `kind: "quote"` check in the same stored report; one migration widens the review-reason CHECK.
- PII in code, not just the prompt: `payment_method` (brand only) and `payment_card_last4` (exactly four digits); `mask_payment_fields` runs before anything is stored or logged, and corrections get the same rule as 422s. Every evidence quote of every field is also swept for card-shaped numbers (13-19 digits passing Luhn), because the payment line is the natural quote for `amount_paid` and `total` (decided in the B4 review, 2026-10-15).
- Tax lines are `(label, rate, base, amount)`; every printed tax line goes in `tax_lines`.
- The demo seed keeps replaying the committed v1 Sonnet run for 001-025; new documents 026+ replay the newest committed v2 artifact, else label plus gold evidence, tagged and counted.
- Pre-registered acceptance bar for making v2 the default: per model, core accuracy (the 7 v1 fields on 001-025) no worse than its v1 run by more than one field; 0 residual schema violations; Sonnet evidence coverage >= 95%; no `max_tokens` stops; no unmasked card number in the artifact.
